# Nawa Copilot — เนื้อหาบทเรียนโปรเจค (สำหรับทำเสียงบรรยาย)

เอกสารนี้คือเนื้อหาสไลด์ 37 หน้าเรียงตามลำดับ แต่ละหน้ามี “บนสไลด์” (ข้อความที่ผู้ชมเห็น) และ “คำอธิบาย” (สิ่งที่ผู้บรรยายควรพูด)

บริบท: Nawa Copilot เป็นโปรเจค portfolio ของ พรพจน์ หมั่นดี — ผู้ช่วย AI ด้าน HR/IT สำหรับบริษัทสมมติ Nawa Tech สร้างใน 8 สัปดาห์ ใช้ Azure OpenAI (gpt-5-mini), RAG ภาษาไทย, Text-to-SQL กับ PostgreSQL row-level security, LangGraph, MCP และ deploy บน Azure Container Apps ข้อมูลทั้งหมดเป็นของสมมติ

## สไลด์ 5: LLM = โปรแกรมที่ “เดาคำถัดไป” เก่งมาก

**บนสไลด์**
- พื้นฐาน 1 · LLM คืออะไร
- LLM = โปรแกรมที่ “เดาคำถัดไป” เก่งมาก
- ถูกฝึกจากข้อความมหาศาล จนเขียน ตอบ สรุป แปล และเขียนโค้ดได้
- ในโปรเจคนี้ใช้ gpt-5-mini ที่ Microsoft รันให้บน Azure — เราแค่ส่งข้อความไป แล้วได้ข้อความกลับมา
- จุดอ่อน: ไม่รู้ข้อมูลบริษัทเรา · บางทีแต่งเรื่องเอง · คิดเลขพลาดได้ · ไม่รู้ว่าใครเป็นใคร
- เราส่ง →
- “นโยบายลาป่วยของ Nawa Tech คืออะไร”
- ← โมเดลตอบ (ถ้าไม่ช่วยมัน)
- “ปกติบริษัทให้ลาป่วย 30 วัน…” (เดาเอา!)
- ทั้งโปรเจคคือการ “ปิดจุดอ่อน” 4 ข้อนี้ด้วยระบบรอบตัวโมเดล

**คำอธิบาย**
LLM ย่อมาจาก Large Language Model หลักการคือทำนายคำถัดไปทีละคำ ฟังดูง่ายแต่พอทำได้เก่งมากก็ดูเหมือนเข้าใจภาษา จุดอ่อนสี่ข้อคือ ไม่รู้ข้อมูลภายในบริษัท แต่งเรื่องเมื่อไม่รู้ (hallucination) คิดเลขพลาด และไม่มีแนวคิดเรื่องสิทธิ์ของผู้ใช้ งานทั้งหมดในโปรเจคคือการแก้สี่ข้อนี้: RAG แก้เรื่องไม่รู้ข้อมูลและแต่งเรื่อง, การคำนวณด้วยโค้ดแก้เรื่องเลข, login + RLS แก้เรื่องสิทธิ์


## สไลด์ 6: เราคุยกับโมเดลผ่าน “prompt” และจ่ายเงินตาม “token”

**บนสไลด์**
- พื้นฐาน 2 · Prompt, token และค่าใช้จ่าย
- เราคุยกับโมเดลผ่าน “prompt” และจ่ายเงินตาม “token”
- Prompt
- ข้อความที่ส่งให้โมเดล มี 2 ส่วน: system = กฎ/บทบาท และ user = คำถาม
- Token
- หน่วยย่อยของข้อความ (ประมาณพยางค์) โมเดลนับทั้งขาเข้าและขาออก
- ค่าใช้จ่าย
- จ่ายตาม token ที่ใช้จริง ไม่ใช้ = ไม่เสีย คำถามหนึ่งข้อของเรา ≈ 0.04 บาท
- src/copilot/llm.py → chat(messages, purpose)
- · จำกัด token ขาออก (กันค่าใช้จ่ายบานปลาย)
- · บันทึก token + ค่าใช้จ่ายทุกครั้งลง logs/llm_usage.jsonl

**คำอธิบาย**
ทุกการเรียกโมเดลในโปรเจคผ่านฟังก์ชัน chat ตัวเดียวใน llm.py ข้อดีคือคุมทุกอย่างได้ที่จุดเดียว: จำกัดจำนวน token ขาออก, ตั้ง reasoning_effort ให้ต่ำเพื่อลดเวลาและเงิน, บันทึกค่าใช้จ่าย, และจับกรณีที่ตัวกรองของ Azure บล็อกคำถาม การออกแบบแบบ “ประตูเดียว” แบบนี้ทำให้เพิ่ม Langfuse ในสัปดาห์ 6 ได้ง่ายมาก เพราะแก้ที่เดียว


## สไลด์ 7: Embedding = แปลงความหมายเป็นพิกัดตัวเลข

**บนสไลด์**
- พื้นฐาน 3 · Embedding
- Embedding = แปลงความหมายเป็นพิกัดตัวเลข
- ข้อความแต่ละชิ้นถูกแปลงเป็นตัวเลข 1,024 ตัว (เวกเตอร์) ข้อความที่ความหมายใกล้กันจะได้พิกัดใกล้กัน แม้ใช้คำต่างกัน
- ใช้โมเดล bge-m3 (ฟรี รันในเครื่องเรา รองรับภาษาไทย) และเก็บเวกเตอร์ใน Postgres ด้วย pgvector
- “ลาป่วย”
- “ป่วยไม่สบาย หยุดงาน”
- “เบิกค่าโรงแรม”
- พื้นที่ความหมาย (ย่อจาก 1,024 มิติ)

**คำอธิบาย**
Embedding คือหัวใจของการค้นหาแบบเข้าใจความหมาย ถ้าผู้ใช้พิมพ์ “ไม่สบายหยุดงานได้กี่วัน” แม้ไม่มีคำว่า “ลาป่วย” ก็ยังเจอนโยบายลาป่วย เพราะพิกัดใกล้กัน ความใกล้วัดด้วย cosine similarity เราเลือก bge-m3 เพราะรองรับหลายภาษารวมทั้งไทย ฟรี และรันในเครื่องได้ ข้อมูลเอกสารไม่ต้องส่งออกไปข้างนอก ส่วน pgvector ทำให้เก็บเวกเตอร์ในฐานข้อมูลเดียวกับข้อมูลอื่น ไม่ต้องมี vector database แยก


## สไลด์ 8: RAG = ค้นเอกสารก่อน แล้วให้โมเดลตอบจากสิ่งที่ค้นเจอ

**บนสไลด์**
- พื้นฐาน 4 · RAG
- RAG = ค้นเอกสารก่อน แล้วให้โมเดลตอบจากสิ่งที่ค้นเจอ
- R
- Retrieval · ค้นหา
- หาย่อหน้าในนโยบายที่เกี่ยวกับคำถามมาสัก 5 ชิ้น
- A
- Augmented · แนบไป
- ใส่ย่อหน้าเหล่านั้นลงใน prompt พร้อมเลขอ้างอิง [1] [2]
- G
- Generation · ตอบ
- สั่งให้ตอบจากหลักฐานเท่านั้น และบอกว่ามาจากข้อไหน
- เหมือนสอบแบบ open book: ไม่ต้องให้นักเรียนท่องจำ แค่ให้เปิดหนังสือหน้าที่ถูกได้ — นโยบายเปลี่ยนเมื่อไหร่ ก็แค่แก้เอกสาร ไม่ต้องสอนโมเดลใหม่

**คำอธิบาย**
RAG ย่อมาจาก Retrieval-Augmented Generation เป็นเทคนิคมาตรฐานของแชทบอทองค์กร ข้อดีคือคำตอบมีที่มาตรวจสอบได้ และอัปเดตข้อมูลได้ทันทีเพียงแก้เอกสาร ความยากอยู่ที่ขั้น R คือค้นให้ถูก ถ้าค้นผิด โมเดลก็ตอบผิดอย่างมั่นใจ สัปดาห์ 2 เราใช้เวลาส่วนใหญ่กับการค้นให้แม่นสำหรับภาษาไทย


## สไลด์ 9: Agent = LLM ที่ได้ “เครื่องมือ” และตัดสินใจเองว่าจะใช้อันไหน

**บนสไลด์**
- พื้นฐาน 5 · Agent และ Tool
- Agent = LLM ที่ได้ “เครื่องมือ” และตัดสินใจเองว่าจะใช้อันไหน
- Tool = ฟังก์ชันที่เราเขียนเอง เช่น “ดู ticket”, “เปิด ticket” โมเดลอ่านคำอธิบาย แล้วขอเรียกพร้อมใส่ค่า
- โค้ดของเราเป็นคนรันจริง — โมเดลแค่ “ขอ” จึงตรวจสิทธิ์ก่อนรันได้เสมอ
- โปรเจคนี้มี 5 ผู้ช่วย: Knowledge · Data · Calendar · Summary · Action และมี Router เป็นหัวหน้าคอยแจกงาน
- โมเดลขอ:
- create_ticket(
- title="Notebook เปิดไม่ติด",
- priority="P2")
- โค้ดเรา:
- เป็นการเขียนข้อมูล → ถามผู้ใช้ก่อน

**คำอธิบาย**
คำว่า agent ฟังดูซับซ้อน แต่หลักคือวนลูป: ส่งคำถามพร้อมรายการเครื่องมือให้โมเดล → โมเดลตอบว่าอยากเรียกเครื่องมือไหน → โค้ดเรารันแล้วส่งผลกลับ → วนจนโมเดลตอบได้ จุดสำคัญด้านความปลอดภัยคือโมเดลไม่ได้รันอะไรเอง โค้ดของเราเป็นคนรัน เราจึงแทรกการตรวจสิทธิ์และการขอยืนยันได้ทุกจุด


## สไลด์ 10: เราไม่ได้ train โมเดลเลยสักตัว

**บนสไลด์**
- ข้อสำคัญที่สุดก่อนเริ่ม
- เราไม่ได้ train โมเดลเลยสักตัว
- งานทั้งหมดคือ “ระบบรอบตัวโมเดล” — เตรียมข้อมูล ค้นหา คุมสิทธิ์ ตรวจความปลอดภัย วัดผล และ deploy
- เปรียบเหมือนเปิดร้านอาหาร: เชฟ (gpt-5-mini) จ้างมาจากข้างนอก ส่วนเราสร้างร้าน จัดเมนู และคุมว่าใครเข้าครัวได้

**คำอธิบาย**
เวลาถูกถามว่า “ทำไมไม่ fine-tune” ให้ตอบว่า ปัญหาของงานนี้คือโมเดลไม่รู้ข้อมูลบริษัท และต้องคุมสิทธิ์การเข้าถึง ซึ่ง RAG และ row-level security แก้ได้ตรงกว่า ถูกกว่า และอัปเดตได้ทันที ส่วน fine-tune เหมาะกับการเปลี่ยนสไตล์หรือรูปแบบคำตอบมากกว่า และถ้าข้อมูลเปลี่ยนต้อง train ใหม่

## สไลด์ 18: “ไม่รู้ ก็บอกว่าไม่รู้” ดีกว่าตอบมั่ว

**บนสไลด์**
- สัปดาห์ 2 · ด่านความเกี่ยวข้อง และการอ้างอิง
- “ไม่รู้ ก็บอกว่าไม่รู้” ดีกว่าตอบมั่ว
- Relevance gate
- ถ้าชิ้นที่ดีที่สุดยังคะแนนต่ำกว่าเกณฑ์ (similarity < 0.5 และ BM25 < 4.5) → ตอบ “ไม่พบในนโยบาย” ทันที ไม่เรียก LLM ไม่เสียเงิน
- เกณฑ์ได้จากการทดลอง 10 คำถาม (calibrate_gate.py)
- เอกสารลับ
- ถ้าคำถามตรงกับเอกสารที่ผู้ใช้ไม่มีสิทธิ์ (เช่น เงินเดือน) → ตอบว่าไม่มีสิทธิ์เข้าถึง และแนะนำให้ติดต่อ HR
- Citation
- โมเดลใส่ [1] [2] แล้วโค้ดแปลงเป็นชื่อจริง “HR-001 §4” — โมเดลแต่งชื่อเอกสารเองไม่ได้

**คำอธิบาย**
ปัญหาใหญ่ของ RAG คือถ้าค้นได้ของไม่เกี่ยว โมเดลจะพยายามตอบจากของไม่เกี่ยวนั้น ด่านความเกี่ยวข้องแก้ปัญหานี้ด้วยการวัดคะแนนก่อนส่งให้โมเดล เกณฑ์ 0.5 และ 4.5 ไม่ได้เดา แต่ได้จากการรันคำถามที่ควรตอบได้และควรตอบไม่ได้ แล้วเลือกจุดตัดที่แยกสองกลุ่มได้ (เรียกว่า calibration) สำหรับ SEC1 มีสองชั้น: เอกสารลับไม่ถูกส่งให้โมเดลเลย และระบบบอกผู้ใช้ตรงๆ ว่าไม่มีสิทธิ์

## สไลด์ 20: SQL ที่ AI เขียน ต้องผ่านกำแพง 3 ชั้น

**บนสไลด์**
- สัปดาห์ 3 · ทำไม Text-to-SQL ถึงปลอดภัย
- SQL ที่ AI เขียน ต้องผ่านกำแพง 3 ชั้น
- แยกคำสั่งด้วย sqlglot: SELECT ได้คำสั่งเดียว · ใช้ได้เฉพาะ view ที่อนุญาต · ห้ามฟังก์ชันอันตราย (pg_sleep, set_config) · เติม LIMIT ให้
- รันด้วย role copilot_reader ในธุรกรรมแบบ READ ONLY และตั้งเวลา 5 วินาที — เขียน/ลบไม่ได้ แม้หลุดด่านแรก
- Postgres ตรวจทุกแถว: เห็นของตัวเอง + ลูกทีมตามผังองค์กร (ฟังก์ชัน my_reports()) · HR เห็นทั้งหมด
- ผลทดสอบ SEC2: หัวหน้าทีม Data ถามข้อมูลทีม Sales → ได้ 0 แถว ไม่ว่า AI จะเขียน SQL แบบไหน

**คำอธิบาย**
หลักคิดนี้เรียกว่า defense in depth ป้องกันหลายชั้น ชั้นหนึ่งพลาด ชั้นอื่นยังกันอยู่ ชั้นที่สำคัญที่สุดคือ row-level security เพราะอยู่ในฐานข้อมูลเอง ไม่ว่าใครหรืออะไรจะส่ง SQL มา ก็เห็นได้แค่แถวตามสิทธิ์ ตัวตนของผู้ใช้ถูกตั้งผ่าน set_config ก่อนรัน และ guard ห้าม AI เรียก set_config เอง เพื่อไม่ให้ปลอมตัวเป็นคนอื่นได้ ตาราง compensation (เงินเดือน) ไม่ได้ให้สิทธิ์ role นี้เลยตั้งแต่ต้น

- ทำงานแทนได้ — แต่ต้องให้คนกดยืนยันก่อนเสมอ
- AI วางแผน
- เลือก tool และร่างข้อมูล
- อ่าน → ทำเลย
- get_ticket, list_my_tickets
- เขียน → หยุดรอ
- แสดงร่างให้ผู้ใช้ดู
- กดยืนยัน
- เซิร์ฟเวอร์ตรวจสิทธิ์อีกรอบ แล้วทำจริง
- MCP (Model Context Protocol) = มาตรฐานกลางให้ AI ต่อกับระบบภายนอก ระบบ ticket ของเรา (NawaDesk) จึงเป็น MCP server ที่ AI ตัวไหนก็ต่อได้ — รวมถึง Claude Desktop
- SEC5: Ploy สั่ง “ปิด IT-1042” → แม้กดยืนยัน เซิร์ฟเวอร์ก็ปฏิเสธ เพราะปิด ticket IT ได้เฉพาะ role it_support

**คำอธิบาย**
เครื่องมือแต่ละตัวใน MCP server มีป้าย readOnlyHint บอกว่าอ่านอย่างเดียวหรือไม่ Action agent ใช้ป้ายนี้ตัดสิน: อ่านได้ทำเลย เขียนต้องหยุดรอ ตัวตนของผู้ใช้ถูกตั้งตอนเปิด server (ผ่าน environment variable) ไม่ได้ส่งเป็นพารามิเตอร์ของ tool AI จึงปลอมตัวเป็นคนอื่นไม่ได้ ถ้าถูกถามว่า “ถ้า AI ถูกหลอกให้ปิด ticket ล่ะ” ตอบได้ว่า ต้องผ่านการยืนยันจากคน และเซิร์ฟเวอร์ตรวจ role ซ้ำทุกครั้ง


## สไลด์ 22: หัวหน้าทีมที่อ่านคำถาม แล้วแจกงานให้ผู้ช่วยที่ใช่

**บนสไลด์**
- สัปดาห์ 4 · Router
- หัวหน้าทีมที่อ่านคำถาม แล้วแจกงานให้ผู้ช่วยที่ใช่
- “ลาศุกร์ 4 ธ.ค. จันทร์เป็นวันหยุดชดเชย นับกี่วัน เหลือพอไหม”
- { "agents": ["knowledge","data","calendar"],
- "knowledge_query": "การนับวันลา",
- "data_query": "ฉันเหลือลาพักร้อนกี่วัน",
- "dates": {"start":"2026-12-04", …} }
- LLM ตอบเป็น JSON แผนงาน พร้อมเขียนคำถามย่อยให้แต่ละผู้ช่วย
- ใช้ reasoning ระดับ minimal → เร็วและถูก
- ปัญหาที่เจอ: ส่งงานให้ Action เกินจำเป็น → แก้ด้วย ตัวอย่าง (few-shot) + กฎ regex → ความแม่นจาก 16/20 เป็น 20/20

**คำอธิบาย**
Router เป็นการเรียก LLM ครั้งเล็กที่สุดในระบบ แต่สำคัญที่สุด ถ้าแจกงานผิด คำตอบก็ผิด เราวัดผลด้วยคำถาม 20 ข้อที่รู้คำตอบว่าควรไปหาใคร รอบแรกได้ 16/20 ปัญหาคือ router ชอบส่งให้ Action agent ทั้งที่ผู้ใช้แค่ถาม ไม่ได้ขอให้ทำ วิธีแก้คือเพิ่มตัวอย่างใน prompt และกฎในโค้ดว่า ถ้าไม่มีคำขอให้ทำอะไร (เช่น “ช่วย…ให้หน่อย”) ให้ตัด Action ออก ได้ 20/20 นี่คือตัวอย่างที่ดีของ “วัดผล → แก้ → วัดใหม่”

- data
- calendar
- summary

**คำอธิบาย**
LangGraph เป็นไลบรารีสำหรับต่อขั้นตอนของ AI เป็นกราฟ แต่ละกล่องเรียกว่า node เส้นคือการส่งต่อ ข้อดีมีสามอย่าง หนึ่ง ผู้ช่วยที่ไม่ขึ้นต่อกันรันขนานกันได้ในขั้นเดียว สอง มีสถานะกลาง (state) ที่ทุก node เขียนผลลงไป และสาม ฟังก์ชัน interrupt หยุดกราฟกลางทางเพื่อรอผู้ใช้ยืนยัน แล้วรันต่อจากจุดเดิมได้ด้วย Command(resume) การคำนวณวันลาอยู่ใน calendar ซึ่งเป็นโค้ดล้วน ไม่ใช่ LLM เพราะเลขต้องถูกเสมอ


## สไลด์ 24: ตัวตนต้องมาจากการล็อกอิน ไม่ใช่จากข้อความในแชท

**บนสไลด์**
- สัปดาห์ 5 · Login
- ตัวตนต้องมาจากการล็อกอิน ไม่ใช่จากข้อความในแชท
- เก็บรหัสแบบ hash
- scrypt + salt สุ่ม — ฐานข้อมูลหลุดก็ไม่รู้รหัสจริง
- ผิด 5 ครั้ง ล็อก 15 นาที
- กันการเดารหัสแบบรัวๆ (brute force)
- ข้อความ error เดียวกัน
- ไม่มีผู้ใช้ หรือรหัสผิด ตอบเหมือนกัน — คนนอกเดาไม่ได้ว่ารหัสพนักงานไหนมีจริง
- Token มีวันหมดอายุ
- JWT ลงลายเซ็น อายุ 30 นาที · พิมพ์ว่า “ฉันคือ admin” ในแชทก็ไม่มีผล

**คำอธิบาย**
ก่อนสัปดาห์ 5 เราเลือก persona จากเมนูได้เลย ซึ่งไม่ปลอดภัย สัปดาห์นี้จึงเพิ่มการล็อกอินจริง scrypt เป็นอัลกอริทึม hash ที่ตั้งใจให้ช้า ทำให้เดารหัสยาก salt คือค่าสุ่มต่อรหัส ทำให้รหัสเหมือนกันได้ hash ต่างกัน ในบริษัทจริงจะใช้ SSO เช่น Entra ID แทน แต่ระบบที่เหลือรับแค่ “User” ที่ผ่านการยืนยันแล้ว จึงเปลี่ยนวิธีล็อกอินได้โดยไม่กระทบ agent ทุกการล็อกอินทั้งสำเร็จและไม่สำเร็จถูกบันทึกลง audit log


## สไลด์ 25: ด่านตรวจที่เป็นโค้ด ทำงานก่อน AI จะเห็นอะไรเลย

**บนสไลด์**

## สไลด์ 27: ลองถามแล้วดูดีไม่พอ — ต้องมีตัวเลขที่เชื่อถือได้

**บนสไลด์**
- สัปดาห์ 6 · ทำไมต้องวัดผลแบบจริงจัง
- ลองถามแล้วดูดีไม่พอ — ต้องมีตัวเลขที่เชื่อถือได้
- ปัญหา 1: ข้อสอบรั่ว
- เราจูน prompt โดยดูผลจากชุดคำถามเดิมซ้ำๆ → คะแนนชุดนั้นสูงเกินจริง (เหมือนท่องข้อสอบเก่า)
- แก้: ชุด held-out ที่เขียนหลังจูนเสร็จ และไม่เคยใช้จูน
- ปัญหา 2: ผลแกว่ง
- AI ตอบไม่เหมือนเดิมทุกครั้ง — คำถาม D06 ผ่านวันหนึ่ง พลาดอีกวัน
- แก้: รันซ้ำ 3 รอบ แล้วนับ pass^k = ผ่านครบทุกรอบ
- ปัญหา 3: ทดสอบแต่ทางดี
- ระบบตอบคำถามปกติได้ ไม่ได้แปลว่ากันการโจมตีได้
- แก้: ชุด red-team 15 ข้อ ลองโจมตีระบบตัวเอง

**คำอธิบาย**
สามปัญหานี้เป็นกับดักที่พบบ่อยที่สุดในการวัดผลระบบ AI ชุด held-out แยกจากชุดที่ใช้พัฒนาอย่างเด็ดขาด เหมือนการแบ่ง train/test ใน machine learning pass^k เป็นตัวชี้วัดที่เข้มกว่าค่าเฉลี่ย เพราะระบบจริงต้องตอบถูกทุกครั้ง ไม่ใช่ถูกโดยเฉลี่ย red-team คือการคิดแบบผู้โจมตี เช่น แอบอ้างว่าเป็น HR หรือสั่งให้รัน SQL อ่านรหัสผ่าน


## สไลด์ 28: ทุกข้อมีเกณฑ์ที่คนอ่านแล้วรันซ้ำได้

**บนสไลด์**

**คำอธิบาย**
หลายโปรเจคใช้ LLM อีกตัวมาให้คะแนน (LLM-as-judge) ซึ่งสะดวกแต่ตัวผู้ตัดสินเองก็พลาดได้และตรวจสอบยาก เราเลือกตรวจด้วยโค้ดล้วน ทุกเกณฑ์อธิบายและรันซ้ำได้ เช่น ตรวจว่ามีตัวเลขจากเอกสารเงินเดือนโผล่ในคำตอบหรือไม่ โดยดึงตัวเลขจากเอกสารลับมาเทียบ การทดสอบ no_write เป็นจุดที่ภูมิใจที่สุด เพราะไม่ได้ทดสอบแค่ว่า AI ไม่ขอทำ แต่ทดสอบว่าถ้าผู้ใช้กดยืนยันจริง เซิร์ฟเวอร์ก็ยังกันได้


## สไลด์ 29: ตัวเลขที่ใช้เล่าได้ในสัมภาษณ์

**บนสไลด์**

## สไลด์ 32: ไม่มีคนใช้ = 0 บาท และไม่มี API key อยู่ที่ไหนเลย

**บนสไลด์**
- สัปดาห์ 7 · ขึ้น Azure
- ไม่มีคนใช้ = 0 บาท และไม่มี API key อยู่ที่ไหนเลย
- Scale to zero
- Container Apps ปิดตัวเองเมื่อไม่มีคนใช้ · แลกกับรอ 2–3 นาทีตอนตื่น
- Postgres เป็น sidecar
- รันคู่กับแอป ไม่มีดิสก์ถาวร ข้อมูลเดโมรีเซ็ตทุกครั้งที่ตื่น · ประหยัด 500+ บาท/เดือน
- Managed identity
- แอปพิสูจน์ตัวตนกับ Azure OpenAI เอง ไม่ต้องเก็บ key ในโค้ดหรือ config
- ตัดสิ่งที่มีค่าใช้จ่ายรายเดือน
- image เก็บที่ GHCR (ฟรี) แทน ACR · ไม่เปิด Log Analytics
- ทุกข้อคือ trade-off ที่เลือกเพราะเป็นเดโม — ของจริงจะใช้ฐานข้อมูลถาวร SSO และเปิดเครื่องตลอดเวลา

**คำอธิบาย**
ทุกการตัดสินใจในหน้านี้เป็นการแลกเปลี่ยน ซึ่งเป็นสิ่งที่ interviewer อยากได้ยิน: scale to zero ประหยัดแต่ช้าตอนเริ่ม, sidecar ประหยัดแต่ข้อมูลไม่ถาวร, managed identity ปลอดภัยกว่า key เพราะไม่มีอะไรให้รั่ว (Azure ให้สิทธิ์ผ่าน role “Cognitive Services OpenAI User”) สคริปต์ deploy รันซ้ำได้ (idempotent) รอบที่สองจะอัปเดตแทนการสร้างใหม่ และไม่เคยพิมพ์ความลับออกหน้าจอ


## สไลด์ 33: คำถามของ Ploy หนึ่งข้อ ผ่านทุกชิ้นที่เราสร้าง

**บนสไลด์**
- สรุป · ทวนครบทั้งเส้นทาง
- คำถามของ Ploy หนึ่งข้อ ผ่านทุกชิ้นที่เราสร้าง
- เว็บส่งคำถาม + token → API รู้ว่าเป็น NT0082 role employee ตรวจ rate limit และงบ
- Guardrails ซ่อนเลขบัตร ตรวจ prompt injection
- Router เลือก knowledge + data + calendar และเขียนคำถามย่อย
- สามผู้ช่วยทำพร้อมกัน: ค้นนโยบาย (RAG) · SQL ผ่าน RLS ได้ 1.5 วัน · นับวันด้วยโค้ดได้ 1 วัน
- Compose รวมคำตอบ คงตัวเลขและ [n] ไว้ → ซ่อน PII ในคำตอบอีกรอบ
- บันทึก audit log → ส่งคำตอบพร้อมแหล่งที่มาและค่าใช้จ่าย
- ใช้เวลา ~5 วินาที · ~0.04 บาท · ทุกขั้นตรวจสอบย้อนหลังได้

**คำอธิบาย**
ถ้าเล่าหน้านี้ได้คล่องโดยไม่ดูสไลด์ ถือว่าเข้าใจทั้งระบบแล้ว ลองฝึกเล่าออกเสียงสัก 3 รอบ ในสัมภาษณ์มักถามว่า “อธิบายสิ่งที่เกิดขึ้นตั้งแต่ผู้ใช้กดส่งจนได้คำตอบ” คำตอบนี้แหละ แผนภาพลำดับแบบละเอียดอยู่ใน docs/architecture.md


## สไลด์ 34: 5 หลักที่ใช้ตลอดโปรเจค

**บนสไลด์**
- ถ้าจำได้หน้าเดียว ให้จำหน้านี้
- 5 หลักที่ใช้ตลอดโปรเจค
- 1. AI เลือกคำพูด — สิทธิ์ ตัวเลข และการแก้ข้อมูล ตัดสินด้วยโค้ดและฐานข้อมูล
- 2. ป้องกันหลายชั้น — ชั้นหนึ่งพลาด ชั้นถัดไปยังกันอยู่
- 3. ไม่รู้ ให้บอกว่าไม่รู้ — และบอกเสมอว่าข้อมูลมาจากไหน
- 4. วัดผลก่อนเชื่อ — ชุดที่ไม่เคยใช้จูน รันซ้ำ และลองโจมตีตัวเอง
- 5. คุมค่าใช้จ่ายตั้งแต่ออกแบบ — จ่ายตามใช้ ปิดเมื่อว่าง มีเพดานงบ

**คำอธิบาย**
ห้าข้อนี้ใช้ตอบคำถามแนว “ถ้าต้องออกแบบระบบ AI ให้องค์กร คุณจะคำนึงถึงอะไร” ได้ทันที และแต่ละข้อมีตัวอย่างจริงจากโปรเจคประกอบ: ข้อ 1 คือ RLS และ calendar, ข้อ 2 คือกำแพง 3 ชั้นของ SQL, ข้อ 3 คือ relevance gate และ citation, ข้อ 4 คือสัปดาห์ 6, ข้อ 5 คือ scale to zero และงบรายวัน


## สไลด์ 35: ศัพท์ที่ต้องอธิบายได้ในประโยคเดียว

**บนสไลด์**
- คำศัพท์
- ศัพท์ที่ต้องอธิบายได้ในประโยคเดียว
- คำ | ความหมายสั้นๆ
- RAG | ค้นเอกสารที่เกี่ยวข้อง แล้วให้ AI ตอบจากเอกสารนั้นพร้อมอ้างอิง
- Embedding | แปลงข้อความเป็นเวกเตอร์ตัวเลข ความหมายใกล้ = ตัวเลขใกล้
- BM25 / RRF | ค้นด้วยคำตรงตัว / รวมอันดับจากหลายวิธีค้น
- Text-to-SQL | ให้ AI เขียนคำสั่ง SQL จากคำถามภาษาคน
- RLS | Row-level security — ฐานข้อมูลกรองแถวตามสิทธิ์ของผู้ใช้
- Agent / Tool | AI ที่เลือกเรียกฟังก์ชันได้เอง / ฟังก์ชันที่เราเปิดให้เรียก
- MCP | มาตรฐานกลางให้ AI ต่อกับระบบภายนอก
- Guardrail | ด่านตรวจที่เป็นโค้ด ก่อน/หลัง AI ทำงาน
- Held-out · pass^k | ชุดทดสอบที่ไม่เคยใช้จูน · ผ่านครบทุกรอบที่รันซ้ำ
- Managed identity | แอปพิสูจน์ตัวตนกับบริการ Azure ได้โดยไม่ต้องใช้ key

**คำอธิบาย**
ฝึกอธิบายแต่ละคำด้วยภาษาง่ายๆ ในประโยคเดียว ถ้าอธิบายให้คนไม่ใช่สายเทคเข้าใจได้ แปลว่าเข้าใจจริง ศัพท์อื่นที่อาจเจอเพิ่ม: chunk (ชิ้นเอกสาร), hallucination (AI แต่งเรื่อง), prompt injection (การหลอกให้ AI ทิ้งกฎ), CI (เทสอัตโนมัติทุกครั้งที่แก้โค้ด), scale to zero (ปิดตัวเองเมื่อไม่มีคนใช้)


## สไลด์ 36: คำถามที่น่าจะเจอ และแนวคำตอบ

**บนสไลด์**
- ซ้อมสัมภาษณ์
- คำถามที่น่าจะเจอ และแนวคำตอบ
- ทำไมไม่ fine-tune?
- ปัญหาคือไม่รู้ข้อมูลบริษัทและต้องคุมสิทธิ์ — RAG + RLS แก้ตรงกว่า ถูกกว่า อัปเดตทันที
- กัน AI รั่วข้อมูลยังไง?
- สิทธิ์อยู่ในฐานข้อมูลและก่อนการค้น ไม่ได้อยู่ใน prompt — AI ถูกหลอกก็เห็นเกินสิทธิ์ไม่ได้
- รู้ได้ยังไงว่าระบบดี?
- held-out รัน 3 รอบ: routing/SQL 100%, red-team 98% — และบอกข้อจำกัดว่าชุดยังเล็ก
- ปัญหาที่ยากที่สุด?
- เลข ticket ของคนอื่นหลุดผ่านตัวอย่างใน prompt — เจอจาก red-team แก้ด้วยเลขที่ไม่มีจริง
- ใช้ AI ช่วยเขียนไหม?
- ใช้ — แต่ผมตัดสินใจเรื่องออกแบบ ทดสอบ และอธิบายได้ทุกส่วน
- ถ้าทำต่อจะทำอะไร?
- คำถามจากผู้ใช้จริง · eval ใน CI · SSO · ฐานข้อมูลถาวร · ตรวจ PII เพิ่ม

**คำอธิบาย**
ฝึกตอบแต่ละข้อออกเสียง 30–60 วินาที ทั้งไทยและอังกฤษ โครงคำตอบที่ดี: ตอบตรงประเด็นก่อน แล้วยกตัวอย่างจากโปรเจค แล้วปิดด้วยข้อจำกัดหรือสิ่งที่จะทำต่อ สำหรับตำแหน่ง Data Engineer ให้เน้นข้อมูล schema RLS การโหลดข้อมูล CI และ deploy สำหรับ Data Scientist / AI ให้เน้น RAG การวัดผล held-out และ pass^k
